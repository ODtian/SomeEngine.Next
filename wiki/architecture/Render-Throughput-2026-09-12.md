# 通用帧时间优化与实测 — 2026-09-12

## 结果与测量口径

本轮没有达到整帧 1 ms。最明确的收益来自大量运动实例的 CPU 数据处理；静态默认与动态光照只有很小的平均差异，不能认定已有可重复的明显加速。

工作目录为 `F:/SomeEngine.Next-render-enhancement`，分支为 `codex/render-enhancement`。改前版本是本轮开始时包含既有未提交修改的工作树，不是分支提交版本。没有重置或提交用户已有修改。

当前启动默认会运动 1024 个网格实例。静态对照能重现约 2 ms，但不能据此认定此前所有约 2 ms 记录都使用同一播放条件。因此本轮分别测静态默认、运动默认和动态光照，不通过关闭运动获得更好数字。

机器为 Xeon E5-2698B v3（16 核、32 线程）、RTX 3080，驱动 610.74，.NET 10.0.12。使用 Release、D3D12、1280×720。保留原场景资源、灯光、材质、分辨率、细分配置、VSM、TAA、cluster LOD/streaming、两阶段遮挡和原有队列配置。

每种条件均按改前、改后、改后、改前的顺序运行，在同一份场景副本中切换程序程序集。运行期间没有并行构建、测试或另一份引擎测量；没有修改电源策略或关闭其他用户进程。工作站环境仍存在运行波动。

三种条件共同使用固定步长 `0.016666667`，避免快慢版本因墙钟推进而在相同帧号经过不同姿态。低开销测量仅记录帧区间和计数，不含操作级追踪、GPU 时间戳、截图读回或 GPU 验证。

静态默认和运动默认采用原来的流水执行，数字是整个帧循环的墙钟间隔，包含循环内实际等待，但不保证当前 GPU 帧已完成。动态光照使用同步帧，每帧还包含 GPU 完成等待。两种执行口径不能横向解释为相同的端到端延迟，也不能把 CPU 与各队列时间简单相加。

## 合并结果

每种条件合并两轮改前数据、两轮改后数据。静态与运动每个版本各 6000 个有效帧；光照每个版本各 2000 个有效帧。以下单位均为 ms。

| 条件 | 改前平均 | 改后平均 | 改前 P50 | 改后 P50 | 改前 P95 | 改后 P95 | 平均降低 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 静态默认，流水执行 | 2.0068 | 1.9484 | 1.9646 | 1.8948 | 2.5059 | 2.5065 | 2.91% |
| 1024 实例运动默认，流水执行 | 6.2438 | 4.4585 | 6.1772 | 4.3446 | 6.8850 | 5.7317 | 28.59% |
| 动态光照，同步帧 | 3.9270 | 3.8678 | 3.7332 | 3.6801 | 5.2468 | 5.0786 | 1.51% |

P50、P95 从保留下来的原始帧时间排序后，以 `(样本数−1)×分位比例` 位置线性插值计算；合并分位数不是两轮分位数的平均。由此与命令行分析器打印的离散位置分位数可能存在末位差异。

静态第一组改善，第二组反而略慢，合并 P95 基本不变，不能宣称稳定的约 3% 收益。光照第二组平均只相差约 0.011 ms，合并约 1.5% 也不应作为可靠的固定收益。运动默认两轮均明显改善，但改后 4.27–4.65 ms 的波动仍在，离 1 ms 很远。

## 保留的改动

### 按已知实体访问已有查询

在现有 ECS 查询接口增加 `TryGetRow`，按实体直接取得查询中的行，仍检查实体存活和代次、组件匹配、块过滤、行过滤以及读写权限。它不建立新的世界副本、索引服务或每帧全量扫描。

渲染提取为当前变换和上一帧变换维护一个常驻查询，在同一次查询内校验变化目标并写入。原路径先对所有运动实体推进历史，随后又逐实体检查和更新同一历史；现在合并这两部分，当前值确实变化才写当前值，停止运动后仍推进一次历史。有用户回调的情况继续走原来的处理路径。Game World 到 Render World 的提取关系不变。

涉及 `src/SomeEngine.ECS/Queries/QueryCursor.cs`、`src/SomeEngine.ECS/World.EntityTableChanges.cs` 和 `src/SomeEngine.Render/Systems/RenderExtractionSchedule.cs`。

### 上传内存读取

在现有映射缓冲区提供 `Read(Span<byte>, int)`。对于原生上传内存，在支持 SSE4.1 时采用对齐的流式向量读取和必要的内存排序；普通内存、托管映射、短范围、不支持的处理器以及重叠复制保持原有复制方式。非对齐首尾不越过映射范围。接口不代替调用方等待 GPU 或处理非一致内存。

实例属性的上一份数据复制、回滚备份和紧密排列属性读取使用此接口。没有增加常驻 CPU 数据镜像，没有减少复制内容，也没有改变实例历史、更新失败回滚或 GPU 同步约定。

涉及 `src/SomeEngine.Graphics/Resources/Mapping.cs` 和 `src/SomeEngine.Render/Instances/RenderInstanceResources.cs`。

### 缩小资源视图失效范围

区分资源描述变化与仅更换底层资源。底层资源更换时继续失效真实视图、参数连接和相关光栅附件，但不再重新接入没有变化的视图描述。访问或活跃性变化不再无条件重建仍然有效的视图；新激活但尚未分配内存的资源仍进入分配路径，重新分配也继续刷新依赖视图。

涉及 `src/SomeEngine.RenderGraph/FrameExecutor.cs`、`FrameMaterialization.cs`、`FrameAnalysis.cs`。图仍然持久，改动来自已有关系和变化集合；没有增加逐帧整图重录、整图比较或编译命中判断，也没有新增 GraphExtension。现有逐帧导入和关系接入没有在本轮全部改写，不能宣称整个调用链已完全完成接口迁移。

一次静态详细追踪中，视图描述接入从约 101 次/帧降到 2 次/帧；部分时间转移到实际视图处理阶段，整帧收益仍以以上低开销数据为准。

## 热点定位与未采用的试验

以下是临时详细追踪或 GPU 探针的定位结果，不是最终低开销整帧数据，也没有从最终帧时间中减去这些成本。

大量运动实例的提取应用阶段从约 3.07 ms 降到约 0.47 ms；实例跨缓冲区复制从约 0.86 ms 降到约 0.04 ms。CPU 更早完成后，实际等待 GPU 的时间增加，因此局部 CPU 节省不等于同等的整帧节省。这些阶段数据来自不同的详细追踪，不能与上表帧时间直接相加或相减。

临时每 16 帧采样 GPU 批次时间戳。默认静态和运动各采集 1600 帧、剔除前 400 帧；光照采集 1200 帧、剔除前 200 帧。默认各有 74 个可读取的暖机后采样，光照 62 个；末尾尚未在复用时读取的结果未纳入统计。

| 条件 | GPU 批次区间并集，约 | 首段开始至末段结束跨度，约 |
|---|---:|---:|
| 静态默认 | 0.70 ms | 1.15 ms |
| 运动默认 | 3.73 ms | 4.21 ms |
| 动态光照 | 1.42 ms | 1.80 ms |

这些是带探针的批次区间，包含屏障与可能的批次内部空隙，不是纯着色器计算时间。各区间独立进行时钟校准，跨队列合并存在校准误差，不能据此给出严格的 GPU 极限或端到端延迟。它们结合 CPU 等待数据，支持“运动默认在 CPU 优化后受 GPU 光栅化显著限制”的判断。

进一步的 pass 采样中，运动默认的硬件可见性光栅 pass 平均约 0.85 ms，软件光栅 pass 约 0.39 ms；每个名称每帧都有两个实例，不能将名称均值视为完整阶段耗时。动态光照中着色约 0.19 ms、continuation cull 约 0.10 ms。当前瓶颈并非只靠减少图依赖分析就能解决。

曾仅在临时场景副本中试验：在阴影深度原子更新前读取当前值，跳过无法改变结果的写入。DXIL/SPIR-V 编译成功后，运动默认硬件光栅 pass 反而约 0.93 ms、软件约 0.41 ms，没有收益，未采用。首次临时编译误用较低目标配置而失败，恢复该资产原有的 SM6.6 配置后完成试验；根目录资产未受该试验修改。最终保留版本没有本轮新增的着色器修改。
