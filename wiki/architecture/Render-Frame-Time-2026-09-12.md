# 1 ms 帧时目标进展

工作树：`F:/SomeEngine.Next-render-enhancement`。目标仍未达成。此记录接续 [场景与画面验证](Render-Scene-Validation-2026-09-12.md)，不将 GPU pass 耗时之和当作整帧时间。

## 测量条件

本机为 Xeon E5-2698B v3（16 核、32 线程）与 RTX 3080，.NET 10.0.12。默认场景保留 1280×720、原 LOD 与细分误差、TAA、VSM、光照及流送设置。仅关闭垂直同步、调试 UI 和窗口显示。性能运行与 GPU 验证、构建、测试分开；低开销采集 2600 帧，剔除前 600 帧。工作站上的其他任务和驱动调度会影响短轮测量。

## 已实现的通用变化

- Graph 表采用分段写时复制，提交与放弃编辑仍保持隔离；运行时索引不再遍历不可变列表树。
- cluster 的常量数据使用 Graph 上传区；未变化的结构数据允许多个在途帧读取同一上传缓冲，写入时选取没有在途读取者的缓冲。
- 参数连接按实际变化刷新，并对重复资源组合复用持久参数绑定；持续变化的数据使用瞬时绑定，缓存容量有上限。
- 外部资源重绑定先更新资源本身，实际变更再使关联视图失效。临时帧标识变化不会单独触发静态参数连接重建。
- 访问范围、队列关系和边界状态相同而资源对象变化时，复用同步关系并重新绑定资源。布局、访问、调度、别名变化仍重新计算。
- `RecordAllThenSubmit` 集中并行录制跨提交批次的工作，并与必须在调用线程录制的工作重叠；提交前等待全部录制完成。应用使用这一模式，Graph 仍支持原有流水提交模式。
- HiZ 前五层在一个线程组内归约，尾部由每视图一个线程组完成；大尺寸中间层仍保留并行归约。最后一个块吸收各层的奇数边缘，保持原最大深度覆盖。默认场景两阶段合计由 12 次 HiZ pass 减至 4 次。
- VSM 页尺寸和跨度已经保证为 2 的幂，用移位、掩码替代采样中的整数除法和取余；负滚动坐标仍向下取整。
- 缺页反馈只复制计数头及实际条目，保留原始报告计数以维持溢出统计；零条目的完成票据仍送达消费端。删除读取缺页队列的 CPU 中转数组。
- 纹理范围排序比较枚举的底层整数，消除比较时的装箱。

## 命令复用与队列调度

已实现 D3D12 原生命令列表复用。渲染回调每帧执行，当前资源、描述符、常量上传及提交序列照常处理。后端收集传给 Silk.NET 的完整命令参数，包括指针指向的数组；命令字节和当前保留的资源身份均匹配时，复用已关闭的命令列表。每个录制资源组最多保留两份原生列表及 allocator。缓存只保存资源的托管身份，不额外保留大缓冲和纹理的原生引用；当前录制仍负责保留 GPU 使用的资源。描述符堆保留原生引用，避免堆地址回收后误匹配。

不支持的命令和原生接口借用会先录制已收集的前缀，再继续正常录制。Bundle、稀疏资源、交换链图像和临时附件描述符的录制不复用。公开的 `RecordedCommands` 仍只能提交一次，allocator 只在此前 GPU 使用完成后重置。

D3D12 命令列表不保留传入资源的引用，allocator 也不能在 GPU 使用期间重置。实现必须维持当前录制对资源的引用、提交序列以及 allocator 的完成条件，且不能延长大纹理/缓冲的缓存引用而破坏内存预算。[Microsoft 命令录制与引用计数说明](https://learn.microsoft.com/en-us/windows/win32/direct3d12/recording-command-lists-and-bundles)、[allocator 重置要求](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12commandallocator-reset)。

详细追踪中每帧约 9 条列表，平均复用 5.67 条，实际重置及关闭约 3.33 条；命令录制 CPU 总时间约从 1.55 ms 降到 1.09 ms。这是跨线程的 CPU 时间总和，不是帧时间。相邻低开销对照如下，两次均值几乎相同，因此没有声称单独复用命令列表已明显提高帧率。

| 原后端第 1 轮 | 2.2736 ms | 2.2532 ms | 2.8684 ms |
| 原后端第 2 轮 | 2.2597 ms | 2.2143 ms | 2.8791 ms |

Graph 新增 `PassQueueSelection.AnyCompatible()`。这种策略先筛选可执行该 pass 的队列，再优先减少前驱队列交接，最后比较可开始时间。指定队列或队列类型的原有策略仍受原约束。cluster 缺页和诊断反馈复制采用此策略，不再固定要求 Copy 队列；未改读取内容、频率、容量或流送逻辑。动态光照与细分验证中的活跃队列从 3 个减到 2 个，计算队列仍使用。

## 共享堆状态修复

合并反馈提交暴露了原有的别名状态问题：一个提交内的资源结果按 CPU 表顺序写回，堆区域据此覆盖“最后使用的资源”，这个顺序可能与 GPU 使用顺序不同。后续禁用或移除别名资源后，Graph 可能误认为先前资源仍活跃，漏掉再次激活。

堆区域现在保留本帧成功提交中、生命周期最靠后的分配；帧号区分前一帧的状态与本帧首次使用。移除、分裂、合并区域仍清理对应记录。原有 cluster“取消帧后增加几何、修改材质、移除几何”的 D3D12 用例能复现旧行为，修复后 D3D12 和 Vulkan 均通过。没有通过关闭别名复用或放宽验证解决问题。

## 阴影队列试验与动态光照 GPU 热点

尝试让阴影、光照计算任务使用兼容队列，以及在调度中考虑后续固定队列的消费倾向。仅放开队列的默认场景对照为 2.1913/2.1673 ms → 2.2058/2.2160 ms；加入后续消费倾向的一轮为 2.0967 ms，但每帧原生提交次数由此前约 4.33 增至 4.67，未证明达到减少提交的目的。动态光照中的改善也不足以证明通用收益，因此这两组队列试验全部撤回。

动态光照采用 `--synchronous-frames --scene-playback motion --fixed-step 0.016666667`，每帧一个网格和一个灯光变化。采集 1200 帧、剔除前 200 帧，原版本均值/P50/P95 为 5.6569/5.3551/7.5773 ms，队列试验版本为 5.4609/4.9769/7.4178 ms。这里包含每帧 GPU 完成等待，不能与默认场景的流水运行直接比较。原版本详细追踪中，GPU 完成等待约 2.29 ms，因而后续必须同时处理 GPU 工作。

使用临时 GPU 时间戳采集 600 帧，并汇总剔除前 200 帧后已完成的结果。计时覆盖 pass 的前后屏障；下面是单个 pass 名称的平均值，不能将不同队列或同名 pass 的平均值相加当作 GPU 整帧时间。

| 动态光照 GPU pass | 平均 |
|---|---:|
| Cluster continuation cull | 0.568374 ms |
| Shade Cluster bin 0 | 0.186499 ms |
| Finalize virtual shadow physical-page HiZ | 0.103718 ms |
| Seed Cluster continuation hierarchy roots | 0.091466 ms |

`cluster_cull.slang` 的 `CullRasterRegions` 由每个候选线程串行扫描目标区域。把世界包围盒变换移到区域循环外的试验，只把上述 cull 时间带到约 0.55 ms，未得到明显整帧收益证据，也已撤回。更大的调整方向是让候选的目标区域工作在 GPU 上并行展开，同时保留原投影/遮挡计算。不能在剔除之前按最终输出容量截断候选与区域的组合，否则可能提前丢掉本应可见的工作；优先评估每候选工作组的区域并行以及对应的间接分派参数。

所有试验代码、GPU 时间戳探针、临时能力开关、着色器和编译资产都已恢复到试验前状态。恢复后 Release 构建通过，动态光照 180 帧 GPU 验证通过，4/4 页驻留，输出哈希仍为 `D0F24B388E6421B0`。本轮没有声称新的性能提升，1 ms 目标仍未达到。

## UE5 源码对照与区域工作分配

后续架构复核发现正常路径仍存在逐帧重放图关系的问题。CPU 后续工作以 [RenderGraph 持久结构原则复核](/F:/SomeEngine.Next-render-enhancement/wiki/architecture/RenderGraph-Architecture-Audit-2026-09-12.md) 为准：先修显式 CRUD 与常驻关系维护，再考虑并行准备，不能以 UE 的逐帧图构建方式替换本项目架构。下文源码对照与 GPU 测量仍对应当时实际结果。

通过已连接的 GitHub 读取 `ODtian/UnrealEngine` 私有仓库。版本文件为 5.8.1，参考提交为 `71fe36aac5a8df5ccd66c763ffc902b29b6a9c43`。以下结论来自这份源码，不能泛指所有 UE5 版本。

本次落地的是区域工作分配，未移植 UE 的整套 VSM 页窗口表示。原来的每个候选线程串行消费区域位图，现在复用引擎已有的 `WaveQueue`，把同一 wave 内有效区域的工作分给所有参与线程。空候选线程也能参与消费；只枚举位图中的有效位，不创建候选与区域组合的全局中间数组，不增加 GPU pass、提交或读回。候选 LOD 筛选、逐区域包围盒投影、HiZ 测试、两阶段恢复和输出容量处理均保留。区域顺序可以变化，和原来的跨线程原子追加一样不保证固定顺序。

改动位于 `assets/Shaders/cluster_cull.slang`，两个阶段的 DXIL/SPIR-V 资产均重新编译。此处没有修改灯光、材质、分辨率、LOD 阈值、细分预算、流送请求或场景内容。

## 以实测成本选择局部批次重组

用户补充允许范围明确、成本合理的局部 reconcile，并要求优先处理影响 1 ms 目标的主要成本。整套图输入接口迁移因此暂停，本次先量化 CPU 与 GPU 工作，没有为了形式上的纯 CRUD 改写整个图。

默认场景详细追踪 900 帧、剔除前 500 帧，0 丢事件、0 scope 错误。详细追踪下平均帧时间为 2.6250 ms，不能和低开销帧时间直接比较。主线程阶段均值为：依赖分析 0.02149 ms、调度 0.00024 ms、frontier/生命周期更新 0.00071 ms、行准备（含子调用）0.26631 ms；原生 Present 0.36340 ms、ExecuteCommandLists 0.31507 ms、Signal 0.06068 ms、Wait 0.04986 ms。跨线程时间没有与主线程相加当作帧时间。因此，“分析未复用”不是当前最大差距，提交和行/绑定准备更值得优先检查。

临时 GPU 时间戳也重新定位了热点，计时包含 pass 前后屏障。动态光照的 continuation cull 为 0.097600 ms，较上一阶段串行区域处理时约 0.568 ms 已明显降低；着色为 0.194326 ms，根播种 0.092809 ms，最终阴影页 HiZ 初始化 0.086674 ms。默认场景着色为 0.165991 ms。以上为各 pass 名称的平均值；同名多 pass 和不同队列不能直接相加视为 GPU 整帧时间。这些探针仅用于定位，未用于下表低开销整帧测量，产品代码中的探针均已移除。

CPU 追踪暴露出三个在途执行实例反复出现 3/6/3 次原生提交，平均约 4 次。多出的 Graphics 批次来自初始化期间曾经需要的拆分：原有局部更新能拆分批次，但在依赖消失后不会合并回来。真实场景中，材质收尾的两个小批次被保留在不同提交阶段，即使它们已不再需要独立提交。

`FrameSubmissions.cs` 现在只把有成员/依赖更新的批次及同队列后继加入候选集合。在已维护的批次依赖图上检查：后面的批次没有引入前面批次原本不具备的前置依赖，前面批次的其他消费者本来也需要后面的批次完成。满足条件才合并相邻同队列批次；变化重新产生跨队列依赖时，仍由原有循环拆分逻辑重新拆开。完成信号和实际资源等待继续由提交路径汇总。没有每帧重建全图，也没有按场景名、节点数量或采样结果设阈值。

## 约 2 ms 的含义与 CPU/GPU 瓶颈复测

用户询问当前约 2 ms 是否为 CPU 与 GPU 相加，以及是否存在直接减半的调整。该数字来自应用 `EngineTrace.BeginFrame` 到对应作用域结束的墙钟时间，是流水运行的帧循环间隔；它包含 CPU 工作及该循环实际等待，并不要求当前 GPU 帧已经完成，因此既不是 CPU 与 GPU 时间之和，也不是端到端显示延迟。动态光照采用的同步帧测试另行等待 GPU，不能和该数字混用。

使用原分辨率 1280×720、默认场景和原有功能配置补测，没有降低画质或更换工作负载。无 GPU 探针的相邻低开销运行，3000 帧剔除前 1000 帧后平均为 2.1784 ms（P50 2.0865 ms，P95 3.0003 ms）。机器运行波动存在，不把此前约 1.94 ms 和这次 2.18 ms 当作代码回退证据。

临时在提交批次的第一个/最后一个 pass 前后插入 GPU 时间戳，以 RHI 的时钟校准映射到 CPU QPC 时轴。同一帧的跨队列区间取并集，避免重复计算并行部分。每个在途执行实例仅在已完成后读取查询结果。最初逐帧测量对 CPU 录制有明显干扰，故改为每 16 帧采样一次；最终 3200 帧剔除前 600 帧，整个运行平均帧循环为 2.1648 ms（P50 2.0628 ms，P95 2.9992 ms），与无探针相邻运行接近。最后几个尚未在下一次复用时读取的结果没有纳入统计。

结合前面的 CPU 阶段成本，这些证据指向当前默认场景主要受 CPU 准备、录制和驱动提交侧限制，GPU 着色吞吐并未占满约 2 ms 预算。GPU 批次工作本身已有约 0.86 ms，首末跨度约 1.11 ms；CPU 侧接近 1 ms 后，GPU 工作与喂入间隙仍需继续优化。此结论仅针对本次默认场景，不能外推所有材质、分辨率和动态场景。

目前没有已验证的单项能直接减半整帧。图依赖分析约 0.0215 ms，无法填补约 1 ms 差距；更大的候选是减少每帧准备/描述连接与重复命令处理，并让 CPU 录制、提交及 GPU 开始执行更早重叠。Present、跨队列同步及真实依赖不是可以直接删除的成本，不能将这些阶段的总和当作保证可获得的收益。该复测没有引入新的产品优化；临时批次时间戳、时钟能力开关和分析脚本在读取结果后移除。
