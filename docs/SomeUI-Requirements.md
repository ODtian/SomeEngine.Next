# SomeUI 整体设计约束

本文记录本次讨论中用户明确的要求，以及候选设计必须同时通过的场景。接口与实现方式由这些要求共同推导。

## 适用范围

框架的 UI 选择固定为 SomeUI 和 ImGui：SomeUI 用于正式 UI、HUD 和未来的编辑器；ImGui 用于临时调试界面。SomeUI 的控件、组合、响应式、主题和 ECS 数据流设计围绕这些产品界面展开。

这项产品边界由 [SomeUI 与 ImGui 的界面职责](adr/0008-someui-and-imgui-roles.md) 记录。

## 已确认要求

1. 从使用需求与 C# 语言语义出发重新设计。
2. 前端指 C# 内部借鉴 SwiftUI、Compose、SolidJS 的写法与组织方式。多个前端可以并存并在组件边界混用；它们只在协调方式上不同，能够统一的部分只做一套，不为 100% 还原原版语法另做多套。
3. 保留自然的 C# 构造、成员赋值、字段读写和控制流；ECS 的真实字段、嵌套数据与 ref 写入是重要使用场景。
4. 视图默认是 struct，所有界面节点（包括内置元素）使用同一套视图机制；源生成器提供同名函数形式。
5. 闭包只在必要处使用：Solid 前端的计算，以及组件主动调用的内容函数。重跑型前端避免每次重跑分配闭包。（原“响应式计算使用 C# 闭包表达”已由 [ADR 0009](adr/0009-struct-views-and-frontend-reconciliation.md) 替代。）
6. 控件扩展通过类型接口实现，避免装箱与委托分派。内置控件与用户控件享有相同的构建、组合、行为和样式能力。
7. 库与用户代码对等：用户通过组合公开部件得到自己的版本，不提供替换、覆盖层或具名内容槽（[ADR 0011](adr/0011-composition-over-replacement.md)）。
8. 内置控件的实现由控件作者写一份，能够服务于不同的前端。
9. 整段声明重跑与局部计算更新都应有适当的表达方式。每个更新环节的重跑条件、跳过依据和复用对象应当明确。
10. 对 Build 的讨论同时覆盖计算身份、节点身份、闭包捕获、闭包创建、资源注册、条件分支、列表重排和生命周期。
11. ECS 变化进入响应式计算、计算结果写入 ECS、行为与主题驱动外观变化，共同构成完整更新流程。非 ECS 数据通过版本单元同样可以被依赖。
12. 每份主要数据有明确的持有者，每个组件只有一个写入方；比较缓存、计算记录与临时修改分别说明用途与生命周期。
13. 公共写法保持简单，类名不加 `Ui` 前缀。额外的表示、适配和编译能力需要通过具体需求说明必要性。
14. 类型与成员按实际数据或行为命名，命名空间表达所属范围。
15. 渲染数据沿 Game world 到 Rendering world 的既有边界流动，并按更新频率区分持久与每帧部分。
16. 只面向 NativeAOT（[ADR 0013](adr/0013-compose-interception-under-aot.md)）。
17. `Build` 支持真正的 `async`/`await`（[ADR 0012](adr/0012-async-build-resumes-in-rebuild-phase.md)）。
18. 状态不限制读写线程，约束按数据组织表达（[ADR 0010](adr/0010-pull-based-versioned-dependencies.md)）。
19. 组件存储（`IComponent` 与 `ISparseComponent` 并列）按访问与变化频率选择。
20. 布局支持多种算法，用户布局与内置布局对等，可以任意嵌套。

## 贯穿场景

应用拥有一份音量数据，同时显示滑杆、圆形旋钮和数值文本。内置滑杆与用户旋钮共享合适的数值行为；旋钮使用用户自己的内部控件、布局与样式。两种 C# 声明风格复用同一份控件实现。

| 操作 | 需要说明的完整行为 |
|---|---|
| 首次创建 | 控件 struct 的含义、实例身份、状态位置、Build 调用、闭包创建和依赖登记 |
| ECS 系统通过 ref 修改音量字段 | 写入记录点、可见时机、观察粒度、计算调度和 ECS 输出提交 |
| 音量变化而数值文本的显示结果相同 | 哪些计算执行，在哪一层依据相等结果复用后续工作 |
| 父声明重新执行 | 子实例保留条件、参数比较、闭包捕获更新与闭包创建成本 |
| 父声明复用既有结果而子控件依赖变化 | 子计算独立执行及其状态和节点的保留 |
| 用户改变旋钮内部结构或行为 | 使用共同扩展能力完成定制，明确旧子树、计算和交互状态的处理 |
| 主题颜色或尺寸变化 | 样式的定义者与来源、依赖收集、样式结果比较、布局及绘制传播 |
| 条件切换、列表增删与重排 | 节点匹配依据、实例状态保持、创建与释放的时机 |
| 控件移除 | 实例数据、响应式订阅、闭包引用和相关资源的释放 |

## 候选设计的核对顺序

先明确控件数据、实例身份和可重执行计算的关系，再贯通创建、读取、修改、传播、提交和释放。随后以同一份控件代码检查定制能力与两种 C# 更新风格，最后检查闭包创建、比较、布局与绘制的执行成本。

每个候选接口都要放回上述完整场景核对。已确定的设计见 [SomeUI 设计总览](SomeUI-Design.md)。
