## 已确认的问题

1. 导入场景构建原先仅在首次复制公共 shader，重建后仍可能加载旧内容。
   当前引擎代码与旧 Sponza 内容实际触发了 11/12 个资源绑定不一致错误。
   导入构建现每次更新并登记公共 shader/pipeline 资产，同时保留场景自己的几何、材质和 World。
2. 每个材质独立创建同一 shader，导致重复管线和无法合并的材质分组。
   加载过程现在将已经创建的对象直接赋给 `Material.Shader` 和纹理属性。
   未增加资源管理集合；资产加载器仍只管理文件。场景释放自己创建的依赖，
   材质释放不会销毁外部传入的共享对象。
3. 渲染图对每条改变的顺序边重复遍历全部上游与下游。
   现在按整批变化各遍历一次；交集可能保守地扩大重新分析范围，但不遗漏依赖。
4. 流送一次改变很多顺序关系，调度原先逐条修复同一区间。
   现在对冲突涉及的区间统一排序，区间外保留原位置。
5. 流送页数增加后，同一次提交里相同读范围的资源边界状态重复重建。
   当前正在验证相邻相同读取的状态计算合并，资源访问声明仍然完整保留。

## 帧末资源回收与完成查询

详细 trace 定位到 Bistro 每帧约 2,330 次 `ID3D12Fence.GetCompletedValue`。
原因包含两条重复路径：每个纹理的帧末回收对象分别保存并检查同一批队列完成条件；
每个纹理完成回调调用 `RenderDevice.TrackSubmission` 时又主动检查回收状态。

现在同一帧登记的回收对象合为一批，只有一组完成条件，实际资源仍各自保存其堆分配信息。
帧取消时仍等待先前已提交的工作，完成回调抛异常也不会漏掉回收登记。
`TrackSubmission` 只登记各队列最大完成值，回收检查使用原有的帧边界 `CollectCompleted`。
这没有增加材质依赖集合，也没有改变持久图拓扑或 Game world → Rendering world 数据通路。

## VSM 精度、几何加载与闪烁（2026-09-30）

在统一平台复现了首帧后长时间细化：原代码将 Bistro 的几何预算设为 64 MiB 时，
首帧之后仍流送 216 帧、23.4 秒，结束时还有 142 个排队请求和 141 个活动请求，报告未收敛。
缺页反馈的丢失计数为零；页堆接近满载，因此这次长等待主要是容量不足后的淘汰和重载。
这次 64 MiB 诊断不能当作性能通过，也不能与 256 MiB 的帧时间计算收益百分比。

同轮原代码在 256 MiB 下可以容纳全部 Bistro 几何，却在首帧前等待全部页面，
首帧约 8.13 秒，首帧后没有剩余流送。现在引擎的默认几何预算与统一平台一致，均为 256 MiB。
当轮首帧等待不可淘汰的粗几何，整批内容能容纳时通过原流送队列预取其余页；
后续架构复查将细节请求来源集中到 GPU 可见性及 LOD 反馈，见本页末尾。
反馈按几何页去重，每轮允许最多 1024 个读取、64 MiB 读取目标。
简化组在细节页及上级页齐备前保留完整的粗几何，齐备后统一交接。
请求也包含视锥外的组成员，避免已驻留的可见细节一直等待未被请求的相邻页。

加载帧还存在两个 CPU 放大因素。每个页的 BVH 指针更新原先反复扫描模型，并形成大量小上传；
现在登记页到节点的索引，直接引用 BVH 存储的字节视图，只更新受影响的模型并合并上传。
页堆按 16 字节分配，旧读取范围却排除了对齐尾部，将连续分配拆成上千个稀疏范围；

VSM 方向光改用实际屏幕像素在光空间的覆盖范围选 clipmap，请求与材质采样使用同一函数，

页和接收单元请求覆盖法线偏移及过滤范围，避免偏移采样进入未绘制的区域。

几何交接还修正了 BVH 单精度误差与粗几何半精度误差的舍入差异。

## 流送帧的架构复查（2026-10-01）

| --- | --- | --- |
| 缺页组展开 | 多个页反复访问同一简化组及祖先，产生重复请求和容器分配 | 每批按模型去重展开组，再按页去重 |
| 页读取与验证 | 缓存命中可能同步完成读取；启动一批读取曾在渲染线程占约 25 ms | 协调器登记整批请求，最多 8 个读取及验证任务同时执行；完成仍进入原队列，逐页保证取消回报 |

## 提交期间消费几何反馈（2026-10-01）
