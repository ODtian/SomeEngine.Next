# 录制调度、持久绑定和 Job 完成通知

本轮修改后的静态默认场景，平均帧时间从 3.6222 ms 降到 2.1342 ms，降低 41.1%；合并样本的 p95 从 5.1326 ms 降到 3.2693 ms。主线程阻塞从约 0.3592 ms/帧降到 0.0068 ms/帧。

主要问题已经定位到两条路径：CPU 录制受 GPU 提交波次限制，以及 Job 完成通知无条件唤醒全部休眠工作线程。频繁的同步资源访问也会完成 Job 状态，因而把正常的查询、准备和系统更新放大成大量线程唤醒与竞争。

**实现**

1. CPU 录制与 GPU 提交依赖分开。持久保存提交顺序和录制批次，允许工作线程提前录制后续提交。主线程只等待当前提交所需的命令。调用线程限制按连续 pass 段处理，不再使整波退回串行。GPU 队列依赖、资源屏障和完成值保持原有约束。发生异常时先收齐所有录制任务，再释放未提交命令；已经接受的提交仍保留完成信息。
2. 参数块按变化更新。持久 pass 只修改回调值或启用状态时，不重连 shader 参数。参数绑定在对应录制批次上创建或更新，未变化时复用已有绑定。D3D12 更新复用未变化的描述符记录和常量存储；在途命令继续持有旧值。描述符位置记录所属参数块，未变化的整个表直接复用；局部覆盖会失效对应表，堆扩容时也处理被截断的表。
3. 任务可执行通知与完成通知分开。只有发布可执行任务才唤醒空闲工作线程；完成状态变化通知真正等待状态的调用者。等待者先取得通知版本，再检查完成条件，入睡前再次核对版本，避免丢失通知。同步资源访问在前驱 CPU 工作完成、但前驱子 fence 尚未完成时，也会收到通知。没有移除资源访问检查或改变 Game world / Rendering world 数据通路。

主要文件：`FrameRecording.cs`、`FrameSchedule.cs`、D3D12 的 `CommandBindings.cs` / `Descriptors.cs`，以及 Job 的 `WorkQueue.cs`、`Scheduler.Completion.cs`、`Scheduler.SynchronousAccess.cs`、`Scheduler.Dependency.cs`、`Scheduler.Execution.cs`。

`PassRecordingMode.WorkerEligible` 的文档现在明确：GPU 资源依赖不会序列化 CPU 回调副作用，回调可能先于前驱 GPU 提交进行录制。调用线程回调仍在执行帧的线程运行；应用的 CPU 数据依赖应在录制前满足。

**对照方法**

- Xeon E5-2698B v3，16 核 / 32 逻辑处理器；RTX 3080，驱动 610.74。
- Release、Direct3D12、1280×720、1024 实例、async compute 开启、关闭 VSync、隐藏窗口、`--static-scene`。
- 应用基于 `aa8d22fe` 的隔离检出。基线已包含上一轮 RG 输入连接和资源绑定优化、VSM 修正；本轮只替换 RenderGraph、Direct3D12、Job 三个 DLL。
- 主工作区另有资产迁移，因此没有将其未完成的资产变化混入基准。基线动态场景的 ECS 声明异常仍是独立问题；本报告不代表动态场景验证。
- 每次新进程运行 2048 帧，舍弃前 512 帧，使用剩余 1536 帧。采集参数为 `--trace-frames-only`，同步记录 ETW 上下文切换和 ReadyThread。用于结论的记录均无丢事件，所有帧标记完整。
- 正式性能采集期间没有并行执行本任务的构建、测试或离线分析。应用以普通权限运行，管理员辅助进程只负责 WPR 启停。

**最终六次对照**

“录制 + Job”使用提前录制和完成通知修正，但保留原有临时参数绑定；用于判断绑定修改的独立影响。

| 顺序 | 版本 | 平均 ms/帧 | p95 ms |
|---|---|---:|---:|
| 1 | 本轮修改前 | 3.8043 | 5.4026 |
| 2 | 录制 + Job | 2.1195 | 3.0661 |
| 3 | 完整修改 | 2.1755 | 3.4014 |
| 4 | 完整修改 | 2.0928 | 3.1449 |
| 5 | 录制 + Job | 2.2478 | 3.3122 |
| 6 | 本轮修改前 | 3.4401 | 4.9824 |

合并同版本的 3072 个样本：

| 版本 | 平均 ms/帧 | 合并样本 p95 ms |
|---|---:|---:|
| 本轮修改前 | 3.6222 | 5.1326 |
| 录制 + Job | 2.1836 | 3.2136 |
| 完整修改 | 2.1342 | 3.2693 |

数据支持整组修改提速。持久绑定相对于“录制 + Job”的均值差约 0.0495 ms，但 p95 没有改善，且运行间存在波动，因此不宣称持久绑定单独有显著提速。它落实了变更驱动的绑定复用，主要整帧收益来自前两条已定位的执行限制。

另一次只替换录制调度的四轮对照，基线为 3.4393 / 3.6549 ms，修改后为 2.9591 / 3.0363 ms，两组均值降低约 15.5%。这说明提前录制本身有效，不是把 Job 通知的收益全部记在 RG 上。

**CPU 计算与等待**

下表来自最终六次采集中的两次基线和两次完整修改。CPU 时间按连续观测窗口除以帧数，包含帧标记间约 0.001 ms 的微小间隔，所以三种 CPU 状态的和与帧 span 均值略有差别。

| 主线程或调度指标 | 本轮修改前 | 完整修改 |
|---|---:|---:|
| 正在 CPU 上运行，ms/帧 | 3.2555 | 2.1231 |
| 阻塞，ms/帧 | 0.3592 | 0.0068 |
| 就绪、等待调度，ms/帧 | 0.0086 | 0.0055 |
| 进程内线程唤醒，次/帧 | 153.03 | 15.40 |

主线程阻塞降低约 98.1%，进程内唤醒次数降低约 89.9%。最终主线程约 99.4% 的观测时间在 CPU 上运行，阻塞约 0.3%，等待调度约 0.3%。这些运行时间仍包含驱动、同步管理与可能的自旋，不等于纯有效计算。

先前用于定位的详细采集也印证了通知路径的影响：`app/ExecuteFrame` 独占阻塞从约 0.3477 ms 降到 0.000034 ms，`app/Prepare` 独占阻塞从约 0.0593 ms 降到未观测到阻塞。详细插桩会改变成本，因此不用这些分项替代最终低开销帧时间。

本轮没有重新测量 GPU 硬件时间戳占空率。上一份报告的约 39% 属于修改前的样本，不能直接套到新版本，也不能仅按帧率变化推算新的 GPU 占空率。

**验证**

- Job：181 项通过，新增覆盖 0 / 1 / 4 工作线程下嵌套完成等待，以及 CPU 数据可读但子 fence 仍未完成的情况。
- RenderGraph：83 项通过，新增覆盖跨 GPU 依赖提前录制、混合调用线程与工作线程录制、两种提交模式、连续帧 GPU 读回，以及录制失败后收齐其他回调。
- ECS Systems：287 项通过；World Job 访问失败封闭行为：1 项通过。
- D3D12 描述符与反射相关行为：26 项通过，包含并发录制/更新、旧绑定寿命，以及局部临时覆盖后的持久绑定 GPU 读回。
- 最终隔离构建完成 64 帧 GPU validation 和输出验证；111 个 live pass、3 条队列，场景、Cluster 驻留与输出检查正常。
- RG 测试共享进程级 EngineTrace。并行测试曾污染零分配与零丢事件检查，现将该测试程序集隔离执行，保留原断言；最终完整运行 83 项通过。
