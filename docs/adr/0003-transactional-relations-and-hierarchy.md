# Keep relation and hierarchy truth canonical and derive inverse views explicitly

SomeEngine represents ordinary relations as canonical edge entities. Every relation type declares parallel, unique-pair, unique-source, unique-target, or one-to-one cardinality and statically chooses directed or undirected endpoint semantics. Every individual edge retains independent stable identity, and single-edge operations address `RelationEdge<T>` rather than an endpoint pair. An undirected relation is one canonical edge with incident adjacency at both endpoints, not a mirrored pair of directed edges. Relation order belongs to an endpoint-role adjacency membership rather than the edge globally: directed outgoing/incoming and undirected endpoint incident positions are independent, while unordered shards store no order metadata and promise no stable live enumeration. Relation structural commands are interpreted once, in stable total order, against an exact detached candidate `WorldStructureRoot`. Immediate commands operate on the last-applied relation generation; deferred endpoint writes retain that applied adjacency until maintenance. A command batch validates the complete deferred canonical image exactly once at its tail, so a legal uniqueness swap is not rejected after only half of the swap and alternating deferred/immediate streams do not repeatedly scan the dirty set. Explicit bulk selectors build one lazy canonical pair/role index per command batch and maintain it incrementally; endpoint destruction consults endpoint-local applied and dirty buckets instead of scanning all edges. The complete canonical edge state, derived adjacency state, journal, allocator image, and publication epoch become visible through one root+epoch publication; a fault discards the candidate, its lookup workspace, and its diagnostics rather than replaying a second time against the published World.

Hierarchy uses the public ECS-native `Parent<D>` plus read-only derived `Children<D>` RelationshipTarget model, with `Parent<D>` as the only canonical relationship truth. A typed domain is an independent Parent/Children namespace, not a membership set: there is no `HierarchyNode<D>`, Join, or Leave state. Each workload defines its own candidate query, and a candidate matching `Without<Parent<D>>` is a root for that workload. The default domain is only a convenience facade over the same typed model.

Parent-to-Children maintenance deliberately has two supported timings. An immediate Parent lifecycle operation invokes an internal relationship hook and returns with Parent, Children, local order, and internal applied-parent state consistent. A deferred operation, including a job-safe writable Parent ref or span, publishes validated Parent changes while Children remains the last-applied inverse until the hierarchy maintenance system runs. Both paths call the same parent-transition kernel; the maintenance system compares current Parent with internal applied-parent state, batches the required transitions, and updates read-only Children. Command-buffer recording is only mutation transport: playback may apply either maintenance timing. A reader that needs fresh Children depends explicitly on the maintenance handle, while a relaxed reader may intentionally observe the last-applied view.

Multi-work-item canonical Parent editing uses versionless detached topology-packet staging followed by one admitted serial finalizer. Packet callbacks receive `LastSystemVersion` only as a query-selection baseline; they never receive `CurrentSystemVersion`, allocate a tick, attach a commit version to staging, or publish World facts. An empty capture or unchanged staged image schedules no Parent/topology writer and consumes no tick. For a changed image, the finalizer first acquires Parent/topology writer admission, validates live membership and Parent preimages, enters the structural candidate, and then obtains the single commit version used by all Parent/Children row facts, coarse watermarks, and journal entries in the atomic publication.

Clock-window baselines and publication versions are separate contracts. `AcquireSystemTick()` advances the clock but returns the prior baseline; `AcquireSystemVersion()` returns the newly advanced version that a writer publishes. Public `ExecuteQuery` does not accept a caller-supplied current version: after exact query admission, a writable query allocates its own new write version and a read-only query does not advance the clock. Generated `IJobEntity` similarly allocates one shared version only for a matching execution whose immutable descriptor contains a direct World write; empty, fully filtered, and matching read-only jobs consume no tick. Hierarchy propagation is stricter still: packet entry is versionless, and only the first actual typed-context `Write` that passes relationship, capability, component-presence, and exact stable-row ownership checks allocates the shared version reused by every packet. Read-only callbacks, declared-but-unused write capability, empty roots, and rejected accesses consume no tick. The no-nested-admission allocator used inside the restricted callback is runtime-internal and does not reopen ordinary World APIs.

Sibling order is local to each parent's Children collection. Ordered parents preserve explicit order; unordered parents allocate no order metadata and make no stable enumeration promise. Ordinary parent destruction orphans surviving direct children, while only explicit subtree destruction or an ownership relation cascades lifetime.

Relation and hierarchy changes use ordinary ECS `Added`/`Changed`/`Removed` tracking. Current consumers use the conservative system `LastSystemVersion` window; a future per-consumer checkpoint may narrow at-least-once repeats but cannot replace these native facts or create a topology-specific stream. Parent changes describe canonical hierarchy edits and Children changes describe inverse maintenance; there is no `RelationChanges`, `HierarchyChanges`, `ParentDelta`, membership delta, or other topology-specific change stream. Writable relation endpoints, relation side-store truth, endpoint-pair-as-edge APIs, edge-global ordering, mirrored undirected truth, writable Children, hierarchy membership tags, and duplicated immediate/deferred maintenance implementations are rejected because they permit ambiguity, hidden order cost, duplicate change models, or divergent invariants.

Runtime-owned bundle callbacks are structural transactions too. A `BundleWriteView` is callback-scoped and byref-like; callbacks write declared storage values only through the view, while captured-World storage writes are rejected and structural reactions are recorded through `World.Commands()` as the next wave. Explicit candidate-tick advancement and callback-scoped journal suppression remain available, and each view write observes their current value. Rows are materialized lazily so a hook cannot scan future default rows, and a lazy index build is rejected while its indexed component is still pending in the current row. Synchronous component hooks read through `DeferredWorld`; captured-World table/shared/topology writes are rejected, while runtime-owned direct buffer/sparse borrows may nest under the already-active topology writer and must still prove exact Job capability when invoked from a Job. Structural/value reactions are recorded through the hook invocation's thread/epoch-scoped `DeferredCommandWriter` for the next wave. Immediate callback and hook code can have ordinary effects outside the World; candidate rollback covers ECS-owned state and the hook command overlay, not captured counters, files, `ref TState`, or leaked Entity values.

The current implementation uses persistent COW for fixed-size entity-location pages and table chunk backing while retaining candidate-private archetype/chunk shells. DynamicBuffer overflow is independently owned per row: forks and structural moves may share an immutable array until that row's first real content write, whose detach preserves capacity, copies only `[0, Count)`, and leaves inactive capacity at `default`; managed overflow keeps inactive inline storage cleared. Each shared-component bucket owns one canonical immutable tuple/backing reused by every bucket chunk and detached fork without exposing a mutable array. Immutable published Children, adjacency, and index-bucket generations may also be shared; remaining mutable owners still use exact detached clones, so extending COW there is only a measured prepare-cost optimization and not a transaction-correctness gap.
