### 较早版本的 GPU 与 CPU 归因

来源：[帧时间与占空率报告](Frame-Duty-2026-09-20.md)。以下数据早于后续录制、Job 和绑定修改。

GPU 查询运行平均帧周期 3.5072 ms：Graphics 0.8286 ms、Compute 0.5307 ms、Copy 0.0033 ms；三队列执行区间并集 1.3625 ms/帧，占 38.85%。主线程运行占 90.41%。这些是时间区间占比，不是 SM occupancy。该次进程全部线程运行时间折合 3.89 个逻辑处理器，即 32 个逻辑处理器的约 12.2%；不能套到 2.1342 ms 的后续版本。

另一份详细插桩运行的平均帧 span 为 3.8633 ms。主线程区间与 ETW 运行时间相交、扣除嵌套区间后：

| 类别 | 独占 CPU 运行 ms/帧 |
|---|---:|
| RG 管理 | 0.5373 |
| RHI 封装 | 0.5896 |
| native API | 1.3773 |
| 渲染系统更新 | 0.3649 |
| 准备系统更新 | 0.3310 |

native 内含 Present 0.3291 ms、ExecuteCommandLists 0.3282 ms、队列 Wait 调用约 0.0544 ms。native 指驱动/API 调用的 CPU 成本，包含录制、提交、展示，不能称为 GPU 执行时间或单纯 draw/dispatch 时间；也没有足够细分数据回答只发 draw/dispatch 占多少。

这些表来自不同版本或不同插桩运行，不能相加或拼成当前一帧。不能用 1.3625 / 2.1342 推算新 GPU 占空率。

## 当前已经符合持久图方向的部分

- `GraphStorage.cs` 的编辑分叉共享不可变集合路径，只复制被编辑的可变行，并非每次编辑复制整图。
- `FrameExecutor.cs` 按变化集合更新行；`FrameAnalysis.cs` 的分析复用由变化标记控制。
- `FrameInputs.cs` 对 buffer 的资源连接/范围、texture 的连接/规格做比较，未变不扩散到消费者访问声明。
- `FrameResourceBindings.cs` 已区分资源对象替换与同步关系变化；`FrameStateCommit.cs` 已区分完成值更新与资源边界语义变化。
- `FrameRecording.cs` 已持久保存录制分组，提前派发工作线程录制；参数块只有变化时创建或更新。
- `ClusterPipelineSystem.cs:394` 的 reconcile 有拓扑版本和材质变化门控；`SetPassEnabled` 在值相同时直接返回，`SetPassData` 不重建拓扑。
- D3D12 已有 pipeline/root 状态去重、持久参数数据和整表描述符复用。不能把它描述成所有参数和描述符每帧重新分配。

## 剩余的具体问题与改法

### 1. 关闭功能仍录制、执行透传 pass

`RuntimeApplication.cs:1017` 关闭透明合成，1022 使用无调试显示模式；但 `TranslucencyFeature.cs:183` 始终开启清理与合成，`DebugFeature.cs:168` 始终开启绘制。对应 shader 在关闭状态只返回输入颜色。

建议：在功能开关变化的帧边界，显式把下游颜色输入接到上游，停用透明清理、透明合成和调试透传三个 pass。打开时恢复连接。需要同时修改输出连接和依赖，不能仅关闭写入 pass 后继续读取其输出。确认目标格式和颜色语义一致，并用公开渲染输出验证。

这会确定性减少这三个 pass 对应的录制及 GPU 工作，但节省多少毫秒仍需测量。不要把正常启用的时序功能合并或隔帧来换取数字。

### 2. 常驻材质输入仍按帧全量提供

`ClusterPipelineSystem.Materials.cs:1276` 每帧上传材质标量偏移、标量数据和各 shade 参数；1298 遍历所有材质输入并按名称解析资源。`RenderGraphFrameState.cs:1441` 的参数输入更新无条件标记关联访问行变化；1336 在帧结束清空输入字典。下游比较可以避免真正重连依赖，但前面的解析、查找和行刷新仍执行。

建议：材质标量、纹理/采样器连接、随尺寸或材质分组变化的 shade 参数保存在 Rendering world 所属的持久数据中。由材质或资源变化产生明确的局部更新。相机、时间、当帧计数和真实轮换的上传切片保留逐帧更新。输入分为连接/范围变化、底层对象轮换、内容变化三类，不用一次参数赋值触发三类处理。

必须保留在途旧值的使用寿命；各在途资源副本按自身版本补齐变化，不能简单跳过上传后使用已回收内存。Game world 的变化仍经既有提取路径进入 Rendering world，不增加直接访问通道。

### 3. 任意资源或视图成员变化会重连全部 pass 参数

`FrameExecutor.cs:67` 在资源或视图成员变化时，把全部已有 pass 加入 `_parameterPassChanges`；`FrameRecording.cs:1013` 随后断开并重建这些 pass 的参数连接。

建议：使用已有资源→视图→参数消费者反向索引，更新实际受影响的连接。若原因是稠密行移动，应显式传播移动行对相关消费者的重定位，不能省略正确性修复，也不应靠全 pass 刷新兜底。

这主要影响流式资源、材质加入移除和即时子图变化，不是已证明的静态帧耗时热点。

### 4. 局部调度变化可能扩散到整张连通图

`FrameSchedule.cs:17` 从变化种子同时追踪前驱、后继，重新调度整个连通分量；图较连通时，局部变化也会覆盖大多数 pass。之后还会遍历完整执行顺序重填数组及同队列前后关系。

`FrameRecording.cs:238` 在分组失效时先释放全部录制上下文，再重建所有分组；`FrameStateCommit.cs:92` 在录制不可复用时重建全部资源的提交状态描述。

建议：保留未受影响的执行顺序，只修复违反顺序的受影响区间；同步与寿命沿真正变化的前沿传播，结果不变即停止。提交批次具有持久身份，局部拆分/合并时复用其他批次的上下文、参数表和状态描述。队列配置改变等全局事件仍允许完整求解。

先做输出与公共 API 行为测试：增删材质、开关功能、改变访问范围、流式资源替换、异常后在途资源寿命。性能采集另行判断扩散范围和耗时，不将内部容器布局写成测试约束。

### 5. 持久提交批次还没有承担足够的执行数据

`FrameSynchronization.cs:1220` 每帧按 pass/资源/边界状态收集等待；`FrameRecording.cs:666` 又扫描 pass，收集命令和等待，去重后提交；提交后逐 pass 写相同完成值。`FrameStateCommit.cs:333` 每次提交逐资源比较不含完成值的边界数组。

建议：把固定的命令批次成员、跨队列依赖来源、外部等待来源、展示图像连接、提交后状态写入目标，在结构变化时连接到持久提交批次。每帧填命令结果与完成数值即可。RG 持有资源状态语义，RHI 持有原生命令和在途寿命；派生索引只从主数据产生，不再维护独立事实。

状态转换和完成值仍必须记录。部分提交成功后失败时，必须只提交已接受部分的状态结果，保留现有异常处理行为。不要以“持久图”为理由删除 GPU 同步或资源寿命维护。

### 6. 同步数据的两份表示造成额外补写

`FrameResourceBindings.cs:29` 先更新按资源保存的屏障记录，再标记 pass；`FrameSynchronization.cs:1121` 对变化 pass 清空各列表，从按资源结果重新拼装。仅替换资源对象，也可能导致重新拼装该 pass 的其他资源屏障。

建议：每条同步记录有一个主存储位置，按资源和按 pass 的结构只保存索引；录制使用连续区段。资源对象轮换补写对应记录，只有屏障数量或关系变化才调整区段。连续性与索引间接访问存在权衡，需测量后决定，不能假定一次额外间接访问永远更快。

### 7. reconcile 的范围仍过粗，但不是需要全面禁止

`ClusterPipelineSystem.cs:533` 在 raster/shade 拓扑变化时移除并重新安装整个受影响阶段组，并复制大量阶段集合以回滚。它已有功能区域边界，仍未细化到单个材质阶段。

建议：常见的材质增删、shader 变化用明确操作修改对应阶段、分组及连线；标量变化只更新数据。复杂材质阶段集合、热重载、设备能力重选可以保留有版本门控的区域 reconcile。需保持区域外 pass 身份和资源连接。

即时子图可用于截图/读回、偶发调试、一次性工具工作，内部可以重建；入口、出口、资源访问和完成语义必须显式。不要让小子图变化触发上述全部参数重连或全图录制上下文重建。

## 1 ms 目标的判断与实施顺序

按“整帧周期低于 1 ms”理解，最近一次 2.1342 ms 均值还需下降约 53.1%，p95 还需下降约 69.4%。只说均值达标不足以证明整帧稳定达标；帧周期、CPU 主线程关键路径和 GPU 关键路径需分别报告。

最新数据中 CPU 阻塞只剩 0.0068 ms，因此继续优化等待机制不是首要方向。较早详细样本 native 独占 CPU 已达 1.3773 ms，也提示只优化 RG 管理不足；但该数不能作为最新版本的固定下限。

旧 GPU 每帧执行区间并集为 1.3625 ms，且队列重叠很少。它提示还需削减 GPU 工作或增加真正独立工作之间的重叠；它不是最新 GPU 时间，也不是证明任何架构下都无法达到 1 ms 的下限。当前没有逐 pass GPU 查询数据，不能把整批耗时归给 VSM 或任意首个 pass。

建议顺序：

1. 先恢复当前资产链，完成静态与动态场景的输出验证，补齐同版本低开销帧时间、CPU 调度、GPU 时间戳和详细归因。
2. 去掉关闭功能的透传工作；将常驻材质数据改为变化时上传和连接。优先减少实际工作量。
3. 将提交成员、等待来源和完成值目标持久化，减少每帧按 pass 整理。
4. 修复资源新增的全 pass 参数失效、连通分量调度和全录制上下文重建，重点改善动态帧与尾部耗时。
5. 对仍占主导的 native 录制/提交与 GPU pass 单独优化；对比单队列和 async compute，仅把有可测重叠收益的工作放到异步队列。

可用于约束设计的 CPU 主线程预算示例：RG 0.10 ms、RHI 封装 0.15 ms、native 录制/提交/Present 0.40 ms、应用和准备工作 0.20 ms，留 0.15 ms 余量。这是分配目标，不是预测，也不包含将工作线程耗时相加。若实测驱动或 Present 本身超过预算，就必须调整提交/展示策略或目标环境，不能由 RG 单方面保证 1 ms。

复测至少覆盖静态、每帧运动、单实例变化、单材质参数变化、材质加入移除、资源流入、功能开关和小即时子图。低开销整帧采集与详细插桩归因分开；CPU/GPU 占空率采用同一时间窗，GPU 跨队列取区间并集。公开结果包含平均、p95/p99、分配、命令列表/提交/屏障数量及测量版本。临时原始记录和探针在分析完成后删除，仅保留正式结果。
