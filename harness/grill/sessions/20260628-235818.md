# Grill Session Raw Q&A

## Q: 请梳理从 f:/someengine 迁移到本项目中遇到的问题；先 grill，等问题都澘清后再讨论如何修改 harness；不要因为迁移产生很多临时 harness；先识别当前违反该原则的问题，符合意图的修复是什么？

A: 需要先恢复上下文，读取 wiki/harness 定义和旧 Codex grill session。harness 是强制自动门禁，不是 AI 自报或临时解释。旧仓库是 reference corpus，不是自动产品事实。迁移问题核心是 product boundary、legacy reference、harness boundary 混乱。

## Q: 当前 RHI and RenderGraph 是不迁移啊，因为我已经有新实现了；现在只迁移 Render 和其他，第一次迁移没法编译没法跑是正常的。RHI/RG 第一次迁移还没有怎么办？

A: 不能把旧 Render 里依赖旧 RHI/RG 的 execution 代码照搬进 product boundary，再用临时 harness 放过。正确做法是 Render 领域契约可以迁，旧 Render execution 不迁；execution 以后基于 Next RHI/RG 正式实现并通过 build/test/harness。

## Q: 我不知道哪些 Render 文件容易误迁，你自己工作区帮我整理。

A: 从工作区整理：Components、Data、RenderWorld、material semantic、asset schema、temporal settings 可以作为 backend-free Render domain；RHI/*、FrameResources/ViewHistory、MaterialGpu、Cluster *Pass、RenderContext/PipelineCache、ImGuiLayer 等属于 execution，不应作为旧迁移进入产品边界。灰区文件如 Material.cs、Shader.cs、RuntimeAssetLoader.cs、ClusterPipelineAssets.cs 要按职责拆。

## Q: 有没有更好迁移方法，或者 Render 先不迁移，先等 RHI/RG 进入后再说，然后顺手把 Render 进行一次重构？

A: 更好方法是旧 Render implementation 不按实现迁移；只迁 Render domain contract。Render execution 不是“顺手重构”，而是以后基于 Next RHI/RG 的正式 rewrite。避免两种极端：全搬旧 Render 造成 harness 临时豁免，或完全不沉淀 Render domain 导致未来 big-bang rewrite。

## Q: 具体计划是什么？

A: 计划是让 SomeEngine.Render 成为 backend-free Render domain；旧 Render execution 不进入产品代码；Render execution 以后作为正式产品实现依赖 Next RHI/RG。harness 最终验证 product inventory closure、no undeclared repo-external references、Render backend-free、Cluster domain backend-free、full gate 包含 build、external dependencies declared and verifiable。禁止 fake RenderGraph、disabled migration tests、temporary allowlist、用 Compile Remove 藏旧代码、继续引用 repo 外 SomeECS。

## Q: Cluster 渲染要不要单独拆一个包出来？

A: 要拆，但不能拆成新的混合泥球。Cluster 是 Render 下的 renderer implementation family，不是基础 Render domain，也不是 engine 顶层子系统。应拆成 backend-free Cluster renderer domain/model 与依赖 Next RHI/RG 的 Cluster execution。基础 Render 不依赖 Cluster；Runtime/Editor 可以选择 Cluster。

## Q: 整体来看，还有多少问题需要澄清？

A: 当时统计剩余约 12 个澄清点，其中真正需要拍板的是 RenderGraph 归属、RHI 稳定边界、Render public API、Cluster domain/execution、Runtime/UI/Editor、external 等。随后用户澄清 RHI 仍是旧实现，不应认为存在，使其中多个问题合并。

## Q: 当前 RHI 还是旧实现，不应该认为存在。

A: 修正模型：磁盘上有 src/SomeEngine.Rhi 和 SomeEngine.Rhi.D3D12 不等于 Next RHI 已成立。当前 RHI 是 Legacy RHI，不属于 accepted product boundary。后续不能让 Render/Cluster execution 依赖它。已将 Product Boundary、Legacy Reference、Legacy RHI、Next RHI、Render Domain、Render Execution、Cluster Renderer 术语写入 CONTEXT.md。

## Q: 你推荐的都没啥大问题，下一步干什么？

A: 应把推荐答案视为已接受，不再继续追问。下一步是把 current accepted product boundary 固化：accepted now 包括 Core/Assets/ECS/Job/Runtime/Generators、backend-free Render domain、backend-free Cluster domain/model；excluded now 包括 legacy RHI/RHI.D3D12/RHI tests/window tests、Render execution、Cluster execution、RenderGraph、Editor renderer integration、ImGui/window/present integration、DiligentCore、Diligent-SharpGenTools、非必要 external samples/tests。Animation/Physics/UI 由代码检查后分类；Editor 暂不 accepted 因为引用 legacy RHI 和 external SomeECS。
