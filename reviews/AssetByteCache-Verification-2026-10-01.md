# CPU 字节缓存验证

测量开始于 2026-09-30，完成于 2026-10-01。关联：[索引研究](AssetByteCache-Research-2026-09-30.md)。

**结论：全局哈希 CLOCK 不能作为已有编号入口的默认替代。** 编号 CLOCK 的命中路径明显更便宜；哈希的收益来自稀疏情况下较小的索引容量，不来自更快的寻址。整数 LRU 的命中维护较贵，但本轮混合访问中它减少了重读，整体更快。消除链表不能单独作为选型理由。

本轮完成独立 C# 原型、并发行为检查、真实文件数据重放和项目三场景反馈。原型没有接入引擎缓存或渲染；不宣称完成了 HyperClockCache 移植，也不宣称产品性能验收通过。三场景中 Bistro 未收敛。

## 环境与实现口径

Windows x64，.NET 10.0.12，Intel Xeon E5-2698B v3，16 核 / 32 逻辑处理器。Release、优化开启、TieredCompilation=false、工作站 GC。纯命中最终测量固定在逻辑处理器 8（亲和掩码 256）；文件重放使用默认亲和性。

通过统一的公开原型接口执行读取、插入、清空与预算查询，不测试引擎私有字段。各方案使用相同 16 字节身份输入与内容。全局数字编号预先绑定，编号方案不包含原引擎 ChunkKeys.IndexOf 的线性查找，代表编号寻址的有利情况。输入准备不在命中计时内。

| 名称 | 原型实际存储与操作 |
|---|---|
| 普通引用基线 | 数字编号直接读取 byte[] 引用数组；没有访问标记和淘汰，仅用于命中成本基线 |
| 编号 CLOCK | 一个完整引用数组、访问字节数组、占用位图；按编号读取，预算不足时沿位图寻找候选 |
| 哈希 CLOCK | 连续结构体数组、开放寻址、完整键比较、访问字节；记录复用用写入版本和读屏障保护键与数组的一致性 |
| 整数 LRU | 连续记录数组中的前后整数、复用位置数组、Dictionary<身份,int>；命中加锁并更新顺序，无逐条节点对象 |

哈希原型的记录为 40 字节，不是原生 HyperClockCache 的 64 字节记录。它采用一位 CLOCK，而非原实现的引用计数与多级热度，所以结果检验的是布局取舍，不是该原生实现的绝对性能。编号 CLOCK 与哈希 CLOCK 的候选顺序不同。

主体索引内存使用构造期间的线程分配计数，包含容器、数组头、字典存储和协调对象，排除已存在的数据与请求数组。所有命中都读返回数组的一个字节并累计校验和，接口调用、循环、内容访问的共同费用包含在时间内；这些数值不是一条裸引用读取指令的成本。

## 纯命中测量

驻留 4096 条、每条 32 字节。每个进程先预热，然后执行 9 轮，每轮 1048576 次固定种子的随机访问。以三种顺序启动独立进程，表中时间是三个进程轮次中位数的中位数；括号是三个进程中位数范围。稀疏编号使用随机、不重复位置，替代了先前等距位置的初测。

| 声明条数 / 驻留条数 | 方案 | 命中 ns/次 | 主体索引分配字节 | 命中分配 |
|---|---|---:|---:|---:|
| 4096 / 4096 | 普通引用 | 10.52（10.24–11.22） | 32912 | 0 |
| 4096 / 4096 | 编号 CLOCK | 12.60（12.43–18.30） | 37584 | 0 |
| 4096 / 4096 | 哈希 CLOCK | 30.04（29.67–38.46） | 327832 | 0 |
| 4096 / 4096 | 整数 LRU | 74.68（68.09–75.92） | 322776 | 0 |
| 1048576 / 4096 | 普通引用 | 23.67（20.81–23.86） | 8388752 | 0 |
| 1048576 / 4096 | 编号 CLOCK | 25.92（25.38–26.06） | 9568464 | 0 |
| 1048576 / 4096 | 哈希 CLOCK | 30.15（29.94–33.44） | 327832 | 0 |
| 1048576 / 4096 | 整数 LRU | 70.62（66.89–74.01） | 322776 | 0 |

完全驻留时，哈希 CLOCK 命中约为编号 CLOCK 的 2.38 倍成本，整数 LRU 约为 5.93 倍。编号 CLOCK 比普通引用增加约 2.08 ns，主体索引分配多约 14.2%。所以“每条引用内存和访问成本均不得增加”的验收要求仍未满足。

声明 104 万条却只缓存 4096 条时，哈希主体索引约 320.15 KiB，编号 CLOCK 约 9.13 MiB，前者小约 29.2 倍。其命中仍比编号 CLOCK 慢约 4.23 ns。表大小与活跃数据分布会改变局部性，不能把小表的时间套到大表。

每个进程另执行 5 次阻塞且压缩的全 GC。大声明量下，编号 CLOCK 的进程全 GC 中位时间约 3.57 ms，哈希 CLOCK 约 0.60 ms，整数 LRU 约 0.54 ms。这里还包含共同请求和数据根等整个探针进程的费用，不是独立索引 GC 时间，也不是游戏 GC 时间。

## 真实内容与完整重读路径

从 DefaultGame 1024 小球、Sponza、Amazon Bistro 的现有资产文件选取有效数据，合计 105 个单位、29847826 字节。单位上限 1 MiB；选取较大及较小纹理文件中的可用 tile，并选取网格的有效页前缀。覆盖数量：

| 内容来源 | Mesh 页 | Texture tile | 合计 |
|---|---:|---:|---:|
| 1024 小球 | 1 | 3 | 4 |
| Sponza | 25 | 4 | 29 |
| Amazon Bistro | 50 | 22 | 72 |

纹理未命中经公开 AssetFile.ReadBytesAsync 读取并解码。现有部分 Mesh 文件不能被当前 ClusterMeshBlock codec 解码，报 schema 不匹配，因此通过公开 AssetHeader、BinaryDocument、IRangeSource 和 MeshPayloadLayout API 取得并读取有效网格页，没有访问引擎私有实现。页面内容通过预先生成的 SHA-256 与保留数组核对。

访问序列是固定种子生成的重放，不是渲染帧中采集的访问轨迹。先读取样本生成摘要，故操作系统文件缓存已经预热；没有声称测得冷盘性能。各方案使用完全相同的序列和字节预算。文件、描述绑定在计时前建立。

重复序列访问 24 个可装入预算的单位；混合序列 80% 请求来自这组热点、其余来自整个样本；顺序序列循环遍历全部样本。每个组合预热一次后执行 7 轮，表中为总时间中位数。

每个原型共享一个 4 MiB 保留预算，包含主体索引与数据数组的分配大小：x64 数据数组按 align8(24 + Length) 计费。缓存外的源描述、并行读取任务和消费者保留数组不属于缓存保留预算；计时期间这些操作的分配计入全程分配。普通引用基线不参与预算重放，无缓存读取作为另一基线。

| 访问序列 | 方案 | 总时间 ms | 实际重读次数 | 命中率 | 读取有效数据 MiB |
|---|---|---:|---:|---:|---:|
| 重复，1024 请求 | 无缓存 | 134.83 | 1024 | 0% | 74.00 |
| 重复 | 编号 CLOCK | 3.49 | 24 | 97.66% | 1.74 |
| 重复 | 哈希 CLOCK | 3.34 | 24 | 97.66% | 1.74 |
| 重复 | 整数 LRU | 3.48 | 24 | 97.66% | 1.74 |
| 混合，2048 请求 | 无缓存 | 511.17 | 2048 | 0% | 221.27 |
| 混合 | 编号 CLOCK | 304.44 | 615 | 69.97% | 113.23 |
| 混合 | 哈希 CLOCK | 298.21 | 626 | 69.43% | 113.47 |
| 混合 | 整数 LRU | 288.00 | 555 | 72.90% | 108.88 |
| 顺序循环，2048 请求 | 无缓存 | 1615.52 | 2048 | 0% | 563.08 |
| 顺序循环 | 编号 CLOCK | 1603.74 | 2048 | 0% | 563.08 |
| 顺序循环 | 哈希 CLOCK | 1614.10 | 2048 | 0% | 563.08 |
| 顺序循环 | 整数 LRU | 1614.72 | 2048 | 0% | 563.08 |

重复访问时，三种缓存减少了 1000 次重读，整体约快 39–40 倍；数十纳秒的命中差异没有形成稳定的重读路径时间排名。混合访问时，LRU 比编号 CLOCK 少读 60 次、比哈希 CLOCK 少读 71 次，最终较快。顺序循环中三种策略均没有避免重读，不能把小幅时间差当作缓存成功，也不推断其他淘汰策略同样无效。

倒序复测前的一轮有效数据预算结果也得到相同混合重读计数（615、626、555）。加入数组头计费后，候选和重读计数在此样本中未变。两轮过程时间有所波动，故以最后一轮表格为报告结果，保留重读计数作为机制证据。

预算压力下的扫描费用可见，不能省略：

| 顺序循环 | 主体索引字节 | 淘汰数 | 检查候选记录数 | 另查位图字数 |
|---|---:|---:|---:|---:|
| 编号 CLOCK | 1176 | 2044 | 4088 | 4386 |
| 哈希 CLOCK | 10392 | 2044 | 65742 | 0 |
| 整数 LRU | 7960 | 2044 | 2044 | 0 |

此重放为哈希表和 LRU 配置足以容纳全部 105 个样本的记录容量，排除条目数上限，只由字节预算回收；哈希表有 256 个位置，空位置也有扫描代价。更紧的容量估计会改变空位扫描与数量上限，不能将这一配置的扫描量当作所有哈希 CLOCK 的常量。

## 行为检查

三种缓存各通过 8 个并发读取者、96000 个随机请求，检查返回完整身份和内容；数据单位大小不一，预算包含索引、数组头和对齐。还通过以下接口行为：同键并发读取仅执行一次后端读、单个等待者取消不停止另一个等待者、读取失败可重试、缓存淘汰及 GC 后消费者已持有的数组仍有效、超预算单位不加入缓存。成功记录不依赖弱引用。
